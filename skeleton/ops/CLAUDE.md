## The schema rule

`{{PROJECT}}-ops/docs/schema/types.ts` is the ONLY place a data type may be
changed.

Every product repo holds an exact copy, updated in the same work cycle as
the canonical file:

{{SCHEMA_COPY_LIST}}

Never edit a copy.

`scripts/check-schema.sh` runs before any commit touching data shapes, and
in every product repo's CI. It exits 1 on drift and prints the diff.

Repos sharing a data shape drift within a week. When they do, the drift
surfaces as a runtime bug in production rather than a type error in CI.
That is the whole reason this repo exists.

Schema changes are additive: new fields are optional, nothing is renamed,
nothing changes type. A change that cannot be additive ships with a tested
migration in the same pull request.

All timestamps are epoch ms `number`, never a database `Timestamp`. The
same type crosses the wire to the dashboard without a converter, and a
latency metric is a subtraction.

## Conventions

- TypeScript strict everywhere.
- Conventional commits.
- `main` deploys to staging. `prod` deploys to prod and only moves on the
  founder's go after a staging test. Every change goes through a pull
  request that Claude opens and merges when the gates are green, without
  asking. Delivered means on `main`. The founder is asked one thing, go
  prod. See `docs/workflow.md`.
- All copy in {{COPY_LANGUAGE}}, by the rules in `BRAND.md`. Read that file in
  full before writing anything a user will read.
- Design tokens are never hardcoded. They come from `docs/design-system.md`,
  which is a placeholder until the tokens are supplied. Until then build
  with Tailwind defaults; do not invent brand values as a stand-in.
- Every feature lands with a happy-path test, error logging, and a line in
  `docs/decisions.md` if an architectural choice was made.
- No unbounded loop over data, ever. A bound is a constant a test can
  assert.

## Workflow

`docs/workflow.md` is the working agreement: the founder specs with a
mockup and tests on staging, Claude builds and merges, one human decision
remains and it is go prod. Every release to staging comes with an
acceptance journal in `docs/acceptance/`, written from the template there.
Prod waits for a filled journal. One goal per session. Findings outside
that goal go to `docs/bugs.md` as one line and are left alone.

## Upstream to mainBrain

This repo was generated by mainBrain, and mainBrain generates the next
project. A structural improvement made here and left here is lost to every
project after this one. So:

**What is structural.** Anything the skeleton owns: a CI workflow, a
deploy workflow, a script under `scripts/`, the harness under `.claude/`
(hook, settings, security guidance, patterns), a skill addendum, a
convention in a CLAUDE.md, a section of `docs/workflow.md`, the acceptance
template, a rule in `firestore.rules` that every project needs, a token or
schema check. `.mainbrain/manifest.json` lists the exact files, per repo.
Feature code, product copy, the schema's types and `docs/product.md` are
not structural.

**The rule.** A structural change lands in two pull requests in the same
session: one here, one in mainBrain (skeleton, library or handoff). The
session opens both, merges both on green, and writes the mainBrain commit
in the `decisions.md` line for the change. A structural change with no
mainBrain pull request is not delivered.

**The check.** `python3 mainBrain/scripts/upstream.py <this repo>` lists
every skeleton-owned file this project changed since spawn (to upstream)
and every one mainBrain changed since (to pull down). `--patch` writes the
upstream side as diffs against the skeleton, placeholders restored. Run it
at the start of any session that touches structure, and at the end.

**The direction.** mainBrain wins on the generic; this repo wins on the
specific. A rule that only makes sense for this product stays here and is
written so the reverse render leaves it out.

## Memory

Hierarchical memory at `.claude/memory/`.

**Session start:** run `/mem load` in background to load context.
**During session:** run `/mem save <observation>` when something worth
keeping turns up.
**When stuck:** run `/mem recall <query>` before asking a question that was
already answered.

Structure: `core.md` holds summaries and pointers, `topics/<topic>.md` holds
the detail. Memory is committed to git, so nothing private or secret goes in
it.

## Skills

Installed from the mainBrain library on {{DATE}}. Three kinds live here, and
the difference decides how each one starts.

**Standing directives.** {{STANDING_SKILLS}} apply to every session. The
SessionStart hook in `.claude/hooks/session-start.sh` loads their directives
from `.claude/session-context.md` before the first turn, because a skill
that only triggers on a description match is not enforceable.

**Automatic, via plugin.** security-guidance runs from its own hooks,
declared by the plugin and not redeclared here: a pattern check on every
edit, a model review of the diff at the end of every turn, and an agentic
review on every commit and push Claude makes. Its repo rules are
`.claude/claude-security-guidance.md` and `.claude/security-patterns.json`.
It is the single source of security review.

`.claude/settings.json` names the plugins ({{PLUGIN_LIST}}), but a cloud
session never installs plugins from a repository: the environment's setup
script does (HANDOFF E2). A session whose skill list lacks them runs in an
environment without that script.

**On demand.** {{ON_DEMAND_SKILLS_OR_NONE}} trigger on what the work is.
They stay out of `session-context.md` on purpose: a directive that fires
every session for a tool used once a month is noise.

`.claude/agents/code-simplifier.md` is an agent rather than a skill, so it
is invoked, never loaded.

The order of work on any code change: write, run code-simplifier on the
changed files, run tests, lint and typecheck, commit. security-guidance
reads along at each edit, at the end of the turn, and at the commit.
